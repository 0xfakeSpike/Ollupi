# 可以深入做的方向

这份文档整理 Ollupi 下一步值得做深的地方。依据是 2026-10-18 时的代码（`ea46fff`），每一项都写了现状在代码里的位置，方便核对。

总的判断：Ollupi 现在不缺功能，缺的是把一个难题做到底，以及证明它可靠的证据。`docs/agent-capabilities.md` 里还有五十多项标着"无"或"部分"，但照着补文件编辑、终端界面、插件这些广度项，只会让它更像一个缩水版的 Claude Code，不会增加深度。下面的方向都是往"正确性、可验证、可运维"上做，而不是加功能。

## 总览

| 序号 | 方向 | 规模 | 优先级 |
| --- | --- | --- | --- |
| 0 | 修正 README 里"可以按原样回放"的说法 | 很小 | 立即 |
| 1 | 崩溃一致性与工具副作用 | 大 | 最高 |
| 2 | 确定性回放与回归评测 | 中 | 高 |
| 3 | 核心状态机的测试：性质测试、模糊测试、崩溃注入 | 中 | 高，和 1 一起做 |
| 4 | 调度、限流、重试和背压 | 中 | 中 |
| 5 | 可观测性：链路追踪、指标、费用 | 中 | 中 |
| 6 | 用真实 usage 校准 token 估算（已做按模型的增量校准，误差统计未做） | 小 | 中 |
| 7 | 存储扩展：不再启动时全量加载 | 中 | 低 |

建议顺序：0 → 1 + 3 → 2 → 6 → 4 → 5 → 7。

## 0. 修正 README 里"可以按原样回放"的说法

**现状。** README 开头写"组织成一条可以完整回放的执行链路"，"执行过程全链路记录"一节写"整个会话可以按原样回放"。但代码里没有任何回放实现：每一步都落成了 thread item，这是"完整记录"，不是"可以回放"。

**做法。** 在方向 2 做完之前，把措辞改成"每一步都先落成记录，整个会话可以完整审计"。等回放器做好了，再改回"可以回放"，并附上测试作为依据。

## 1. 崩溃一致性与工具副作用

这是最值得做深的一项，因为它本质上是一个分布式系统问题，而且 Ollupi 已经有了大部分基础：每一步先落库，再执行。

**现状。** 进程在工具执行中途崩溃，重启后 `agent/store.go` 的 `recoverItems` 会把这次调用标成失败，错误写的是"the app stopped while this call was being handled; it may or may not have taken effect, so check before repeating it"。这个处理是诚实的，但等于把"到底执行了没有"这个问题交给了模型和用户。对拨电话、写 Excel、发消息这类有副作用的工具，模型很可能直接重试，造成重复执行。

另外，`agent/tools/spec.go` 里的 `Annotations` 已经有 `IdempotentHint` 字段，但运行时没有任何地方读它。

**做法。**

先把每次工具调用拆成明确的阶段：已批准、已开始（意图已落库）、已完成或已失败。"已开始"这条记录要带一个幂等键，由 thread、turn 和 item id 派生，在批准时就固定下来，重启后不变。

工具按副作用分三类，由工具自己声明：

- **只读或幂等**：重启后可以直接重跑。
- **可核对**：工具实现一个核对接口，运行时把幂等键交给它，问"这次调用生效了没有"。比如写 Excel 的工具可以检查那一行是不是已经写成了目标值；对接外部 API 的工具把幂等键作为请求的 idempotency key 发出去，核对时去查。
- **不可核对**：保持现在的处理方式，标成"结果未知"，但要在记录里明确区分"未知"和"失败"，不让模型把"未知"当成"失败"去重试。

重启恢复时按类别处理：幂等的重跑，可核对的先核对再决定是补记结果还是重跑，不可核对的交给用户。

**怎么证明做对了。** 和方向 3 一起做故障注入：在每一个持久化点前后杀掉进程（测试里可以用一个会在第 N 次 `Save` 时返回错误或 panic 的 `Persistence` 实现），然后重启、恢复，检查两个性质：

- 声明了幂等或可核对的工具，副作用最多发生一次；
- 每个 turn 最后都处在明确的终态，不会卡在进行中。

**规模。** 大。涉及 `thread`（状态和恢复）、`agent/runtime`（执行阶段）、`tools`（新的接口）和 `agent`（恢复流程）。

## 2. 确定性回放与回归评测

**现状。** 每条模型响应、每次工具调用、每个审批和提问都已经落成 thread item，`agent/contextmanager` 按设计只依赖这些 item 来渲染 prompt（为了服务商的前缀缓存，system 和工具列表固定、对话只追加），但"同样的 item 一定渲染出同样的 prompt"目前没有测试保证。缺的是一个能拿记录重跑的执行器。

**做法。**

回放器由两个假实现组成：

- 一个假的 `llm.ChatModel`：按顺序返回记录里的模型输出；同时检查这次发来的 prompt 和当时记录的是否一致，不一致就报告第一处差异。
- 一个假的工具注册表：按记录返回工具结果，不真的执行。

用它重跑一个录下来的会话，检查工具调用序列、审批决定和最终状态是否和原来一致。这样就成了一份回归测试：以后改上下文压缩、脱敏规则、权限规则或 prompt 模板时，能直接看出哪些已有会话的行为变了。

再往上一层是评测：维护一批录下来的会话作为测试集，改动前后各跑一遍，统计工具调用次数、token 用量、任务是否完成这些指标的变化。这里需要真的模型，所以不是确定性的，要单独作为评测跑，不进普通测试。

**怎么证明做对了。** 把现有测试里的会话录成样本，回放结果必须逐条一致；再故意改一处 prompt 渲染，回放器要能准确指出第一处差异。

**规模。** 中。主要是新代码，基本不需要改已有逻辑。

## 3. 核心状态机的测试

**现状。** 业务代码约 12700 行，测试约 5300 行，比例不低，但分布不均：

| 包 | 代码行数 | 测试行数 |
| --- | --- | --- |
| `thread`（核心状态存储） | 1070 | 0 |
| `tools`（工具注册） | 612 | 0 |
| `pkg/jsonrpc` | 195 | 0 |
| `pkg/sqlite` | 79 | 0 |

`thread` 是整个运行时的状态核心：turn 和 item 的状态转换、恢复、持久化都在这里，目前只靠上层包的测试间接覆盖。

**做法。**

- **`thread` 的性质测试**：随机生成一串操作（开 turn、记 item、审批、完成、中断、恢复），每一步后检查不变量。比如任何时刻一个 thread 最多一个进行中的 turn；item 的 seq 严格递增；终态不会再变回进行中；保存后重新加载的状态和内存里的完全一致。
- **崩溃注入**：见方向 1。
- **模糊测试**：`pkg/jsonrpc` 的消息解析、`pkg/redact` 的识别和还原（还原必须是识别的逆操作；任意输入都不能 panic）、`contextmanager` 的截断（截断后的 token 估算不能超过预算）。Go 自带的 `testing.F` 就够用。

**规模。** 中。不改业务代码，但很可能会测出真实的 bug，到时要修。

## 4. 调度、限流、重试和背压

**现状。**

- `agent/agent.go`：所有 thread 共用一条全局 FIFO 队列，并发上限写死成 `workers = 4`。
- `pkg/llm/chat.go`：创建 openai 客户端时没有设置任何重试或退避选项，失败重试完全依赖 openai-go SDK 自带的默认行为，Ollupi 自己没有策略。
- `agent/runtime`(当时是 `agent/runner.go`)：每个 turn 的上限写死成工具调用 16 次、模型调用 32 次、连续失败 3 次。
- ~~并行工具调用只给 Agent 子代理开了，普通的只读工具即使互不相关也是串行执行。~~ 已完成：相邻的只读调用并行执行，`ParallelToolCalls` 总是开启。

**做法。**

- 并发上限和每个 turn 的上限改成可配置项，默认值不变。
- 按模型连接（model profile）做令牌桶限流；收到 429 时按 `Retry-After` 退避，其他可重试错误用带抖动的指数退避，重试次数和总时长都有上限，而且每次重试都落成记录。
- 调度从全局 FIFO 改成按 thread 公平轮转，避免一个会话连续派生很多子代理时饿死其他会话。
- 声明了只读的工具允许在同一次响应里并行执行。

**怎么证明做对了。** 用一个可以设置延迟和 429 比例的假服务商做压测，报告吞吐和排队延迟的 p50、p99，以及限流前后的对比。

**规模。** 中。

## 5. 可观测性

**现状。** 每次模型调用和工具调用的 token 用量、上下文统计都记在 item 上，但只能逐条去看，没有聚合，也没有对外导出。

**做法。**

- 用 OpenTelemetry 打 span：turn、每次模型调用、每次工具调用、审批等待，作为一棵树。子代理的 turn 挂在父 turn 下面。
- 指标：排队时长、模型首字延迟、工具耗时、失败率、每个 turn 的 token 数。
- 按模型连接配置单价，算出每个 turn 和每个会话的费用。
- 导出接口做成可选的，库本身不强依赖某个后端。

**规模。** 中。

## 6. 用真实 usage 校准 token 估算

**现状。** `pkg/llm` 的 `EstimateTokens` 是一条启发式规则：ASCII 字符每 4 个算 1 个 token，每个非 ASCII 字符算 1 个 token。每次模型调用前的估算（`contextStats.estimatedTokens`）和服务商返回的真实用量（`usage.inputTokens`）记在同一个 item 上。`contextmanager` 已经用它们校准：找同一模型在上次压缩后最近一次请求，用它的真实 prompt tokens 加上估算值从那时起的增量（`contextStats.calibratedTokens`），自动压缩和超限判断都看这个数。没有可用的参照时（新会话、刚压缩完、换了模型）仍然只有估算；增量部分、记忆和技能目录的预算、单条工具结果的截断也仍然按估算。

**做法。** 先用已有记录算出估算值和真实值的误差分布，按模型和语言分开统计。如果误差大，再按模型给估算加校准系数，或者接入对应模型的分词器。

**怎么证明做对了。** 给出校准前后的误差数字。这一项数据现成，成本小，结论也很具体。

**规模。** 小。

## 7. 存储扩展

**现状。** `agent/thread` 的 `load` 会在启动时返回所有 thread 的全部 turn 和 item，`thread.Store` 全部放在内存里。会话一多、单个会话一长，启动时间和内存占用都会线性增长。

**做法。** 启动时只加载进行中的 thread 和会话列表需要的摘要，其余按需加载、用完淘汰；长会话在压缩点之后可以做快照，加载时不必从头读起。

**规模。** 中。在会话量真的上来之前，优先级最低。

## 不建议现在做的

文件读写和编辑、搜索、终端界面、IDE 插件、插件系统、斜杠命令这些，都是能力清单里的广度项。它们有用，但其他 agent 都已经做得很成熟，补上之后 Ollupi 也只是"又一个有这些功能的 agent"，体现不出深度。等上面几项做完、核心可靠性有了证据，再按应用的实际需要来补。
